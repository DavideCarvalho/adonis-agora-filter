Not every listing is a Lucid query. An operations console may read from an in-memory store, an
engine client, or a predicate bag under construction — and it should still filter with the same
class style, the same envelope, and the same error shapes as a model listing. That is what the
generic base is for: `BaseFilter<TQuery>`, shared with [filter classes](/docs/filter/guides/filter-classes).

## The shape

```ts title="app/durable/run_filter.ts"
import { BaseFilter } from '@adonis-agora/filter'

export class RunQueryDraft {
  readonly query: RunQuery = {}

  narrow(patch: RunQuery) {
    Object.assign(this.query, patch)
  }
}

export class RunFilter extends BaseFilter<RunQueryDraft> {
  declare $query: RunQueryDraft

  status(value: unknown, operator: string) {
    const values = (Array.isArray(value) ? value : [value]).map(String)
    this.$query.narrow(values.length === 1 ? { status: values[0] } : { statuses: values })
  }
}
```

```ts title="app/controllers/runs_controller.ts"
import { applyCustomFilter } from '@adonis-agora/filter'

export default class RunsController {
  async index(ctx: HttpContext) {
    const draft = new RunQueryDraft()
    await applyCustomFilter(draft, RunFilter, ctx)
    return engine.listRuns(draft.query)
  }
}
```

A method's name IS the key it owns; it receives `(value, operator, field)` — the same call the
model form makes. `setup()`, `$input`, `$parsed`, `$ctx` and container resolution all behave
identically.

## What differs from a model filter

Two things, both load-bearing:

- **There is no declarative path.** A model filter applies `static filterable` columns to SQL for
  you; a draft has no SQL, so every key needs a method — which is the tightest allow-list there
  is. A dotted field falls back to its head segment (`attr.tier` reaches `attr` with the full
  field), so one method owns a whole dynamic subtree.
- **Unknown structured fields fail loudly.** `InvalidColumnFilterError` (a `400` at the
  controller) instead of a silently widened listing — which matters wherever the matched set is
  acted on, not just displayed. Bare legacy keys (`?tag=etl`) stay lenient: unknown ones are
  ignored, so endpoint mechanics like `limit` keep working.

`OR` groups are rejected for the same reason: a draft is an ANDed predicate bag and cannot
express cross-field OR. `AND` groups recurse.

## Serving the list over HTTP

Every list endpoint speaks the same wire format, whatever the store behind it:

| Concern | Request | Helper |
|---|---|---|
| Filter | `filter[field]=v`, `filter[field][op]=v` | `applyCustomFilter(draft, XFilter, ctx)` |
| Sort | `sort=-createdAt,name` | `resolveSort(input.sort, { sortable, default })` |
| Offset paging | `page` (1-based) + `size` | `parsePageParams(qs, { defaultSize, maxSize })` → `offsetPage(rows, { total, page, size })` |
| Cursor paging | `after` / `before` + `first` / `last` | `parseCursorParams(qs, { defaultSize, maxSize })` → `cursorPage(rows, { nextCursor, prevCursor })` |

An endpoint pages one way: offset when the store can count the matching set, cursor for feeds and
stores that cannot count. An unknown filter field, operator or sort field throws
`InvalidColumnFilterError` — map it to a `400`.

### Offset paging

```ts title="app/controllers/runs_controller.ts"
import type { HttpContext } from '@adonisjs/core/http'
import {
  applyCustomFilter,
  InvalidColumnFilterError,
  offsetPage,
  parseFilterRequest,
  parsePageParams,
  resolveSort,
} from '@adonis-agora/filter'

export default class RunsController {
  async index(ctx: HttpContext) {
    const qs = ctx.request.qs()
    try {
      const draft = new RunQueryDraft()
      await applyCustomFilter(draft, RunFilter, ctx)

      const sort = resolveSort(parseFilterRequest(qs).sort, {
        sortable: ['createdAt', 'name'],
        default: '-createdAt',
      })
      const { page, size } = parsePageParams(qs, { defaultSize: 50, maxSize: 200 })

      const { rows, total } = await store.listRuns(draft.query, {
        sort,
        offset: (page - 1) * size,
        limit: size,
      })
      return offsetPage(rows, { total, page, size })
      // → { data, meta: { total, perPage, currentPage, lastPage, firstPage } }
    } catch (error) {
      if (error instanceof InvalidColumnFilterError) {
        return ctx.response.badRequest({ message: error.message })
      }
      throw error
    }
  }
}
```

### Cursor paging

```ts title="app/controllers/events_controller.ts"
import type { HttpContext } from '@adonisjs/core/http'
import { applyCustomFilter, cursorPage, parseCursorParams } from '@adonis-agora/filter'

export default class EventsController {
  async index(ctx: HttpContext) {
    const draft = new EventQueryDraft()
    await applyCustomFilter(draft, EventFilter, ctx)

    const { after, before, size } = parseCursorParams(ctx.request.qs(), {
      defaultSize: 100,
      maxSize: 500,
    })

    const result = await store.listEvents(draft.query, { after, before, limit: size })
    return cursorPage(result.events, {
      nextCursor: result.nextCursor,
      prevCursor: result.prevCursor,
    })
    // → { data, meta: { nextCursor, prevCursor, hasNext, hasPrev } }
  }
}
```

`parseCursorParams` returns `{ after?, before?, size, backward }`: `after` wins when both cursors
are sent, `size` is `first` going forward and `last` going backward, clamped to `maxSize`.
`hasNext` / `hasPrev` default to whether the matching cursor is set; pass them explicitly when the
store knows better. Cursors are opaque strings your store produces — when they are keyset values,
`encodeCursor` / `decodeCursor` give you a URL-safe codec.

### The client side

```ts title="inertia/pages/runs/index.tsx"
import { filterQuery, type CursorPageResponse, type OffsetPage } from '@adonis-agora/filter-client'

// Offset
const runs: OffsetPage<Run> = await fetch(
  `/runs?${filterQuery().where('status', 'failed').sortDesc('createdAt').page(2, 50).toQueryString()}`,
).then((r) => r.json())

// Cursor
const query = filterQuery().where('type', 'deploy').first(100)
const events: CursorPageResponse<Event> = await fetch(`/events?${query.toQueryString()}`).then((r) =>
  r.json(),
)
if (events.meta.nextCursor) query.after(events.meta.nextCursor) // the next request
```

See the [client guide](/docs/filter/guides/client#cursor-pagination) for the full builder surface.

## Testing one

The draft is yours, so the test needs no database and no mock builder — construct the draft,
run the class over a fake ctx, assert the draft:

```ts title="tests/unit/run_filter.spec.ts"
import { applyCustomFilter } from '@adonis-agora/filter'

const draft = new RunQueryDraft()
await applyCustomFilter(draft, RunFilter, { request: { qs: () => ({ tag: ['a', 'b'] }) } })

assert.deepEqual(draft.query, { tags: ['a', 'b'] })
```

<Callout type="info">
If the rows are already in memory (merged from several sources, a static catalog, a remote page),
you do not need a draft at all: [In-Memory Lists](/docs/filter/guides/in-memory) evaluates the full
declarative surface — operators, relations, search, sort, pagination, distinct — over an array.
</Callout>
